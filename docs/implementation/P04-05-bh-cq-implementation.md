## 2. Competency questions

| ID | Query/variables | Frozen expected rows | Proof |
|---|---|---:|---|
| BH-CQ-01 | `vessel, trajectory, unit, observation, observedProperty, phenomenonTime, resultTime, rawRecord, activity` | 18 | SOSA observation belongs to the vessel via `bh:hasTemporalUnit/bh:hasPhysicalBehavior/bh:supportedByObservation`; typed timestamp and PROV source/activity present |
| BH-CQ-02 | `trajectory, unit, segmentIndex, interval, start, end, state, stateClass` | 9 | Three distinct `TemporalUnit` resources, three concurrent Position/Speed/Course description types each; authentic `time:ProperInterval` boundaries, discontinuous coverage preserved |
| BH-CQ-03 | `trajectory, unit, state, stateClass, observation, observedProperty, result, phenomenonTime, resultTime, latitude, longitude, crs, numericValue, quantityUnit` | 18 | Position results expose lat/lon (xsd:decimal) + EPSG:4326; speed (unit:KN) and course (unit:DEG) expose QUDT QuantityValue (xsd:decimal + `qudt:hasUnit`) |

For position rows, `numericValue` and `quantityUnit` must be **unbound**; the P04-03/04 profile stores WGS84 coordinates as named decimal properties, **not** QUDT QuantityValue. Conversely `latitude, longitude, crs` are unbound for speed/course rows. Do not invent position measurement units or convert position data to GeoSPARQL in P04-05.

## 3. Exact binding oracle

SPARQL SELECT variables and every row's RDF terms are compared with **static checked-in** `tests/behavior/expected/bh-cq-0N.json` files. These oracles were authored from the reviewed synthetic six-sample input and segment boundaries, **not generated by executing the same SPARQL query**. They are read-only in normal operation. `docs/standards/P04-05-bh-cq-manifest.json` locks the SHA-256 for each query, expected-results file and the P04-04 fixture, and specifies the base commit.

Comparator guarantees:

1. Exact SELECT variable names **and order**.
2. Exact IRI values and literal **lexical values, datatypes and language tags**; no lossy cast from typed decimal to float or timestamp to local time.
3. **Unbound** variables absent from row bindings (not `null`, zero or `""`).
4. Exact **multiset (bag)** of results: preserves duplicate multiplicity but ignores row iteration order; one wrong row is a failure even when cardinality is unchanged.
5. Non-empty expected oracle and checked-in file SHA-256 are prerequisites; missing inputs yield `BLOCKED`, not `PASS`.

The contract deliberately uses exact literal lexical identity for this deterministic synthetic fixture (e.g., `"8.20"^^xsd:decimal` is not interchangeable with `"8.2"^^xsd:decimal`). This is a fixture-level regression oracle, **not** a global semantic-equivalence assertion for XSD literals.

## 4. Positive and negative evidence

`tests/test_p04_05_behavior_cq.py` executes three positive queries and synthetic negative cases that must be detected:

- Observation property changed to an incorrect value while BH-CQ-01 still returns 18 rows.
- Wrong interval boundary while BH-CQ-02 still returns nine rows.
- Speed unit switched `unit:KN` → `unit:SEC` while BH-CQ-03 still returns 18 rows.
- Longitude perturbed in an otherwise valid position result, with unchanged row count.
- Valid query changed to bind the **wrong property** with the same 18-row cardinality.
- Duplicated binding replacing a correct row, unchanged row count.
- Missing `sosa:resultTime` / altered variable contract / accidental unbound-field replacement.
- Changed fixture or modified golden oracle rejected by SHA checks before query execution.
- `--profile p05` / `p09` returns DEFERRED exit code 2; no silent PASS.

These are data/CQ correctness tests; they do **not** replace earlier BH-V01…V12 validation, nor provide actual observational coverage guarantees.
